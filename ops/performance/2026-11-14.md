# PaceStats performance investigation — 14 November 2026

All implementation and testing used the local `pacestats-dev` Docker environment.
Changes are committed on `codex-perf`; nothing was pushed. The comparison starts
at `b45304d` and the final application build includes `c9b726a`.

## Method

- Built both revisions with the same installed dependencies and
  `npm run build -- --webpack` in isolated directories inside Docker. Development
  compilation was excluded from timings.
- Used the imported local MySQL dataset: 2,982,052 pace rows and 4,350 players.
  The busiest player, `NoFearr1337`, has 21,593 runs. Reset-rate calculations
  joined 2,340,352 rows globally; this player has 18,328 joined rows.
- Ran Chromium inside Docker with **300 ms CDP network latency**, 10 Mbps down,
  5 Mbps up, and **4× CPU slowdown**. Each run used a new browser context.
  Three alternating baseline/final runs provide the browser medians below.
- Disabled browser HTTP caching through request routing. Next router reuse
  remained enabled, so return navigation represents normal application reuse.
  External browser APIs/telemetry were blocked and avatars were stubbed,
  including baseline requests through Next's remote-image proxy.
- Paused the local cron service during measurements. Empty Redis tests used a
  separate Next process and unused Redis database 15. Owned correctness
  fixtures used database 14; neither test cleared the application's database 0.
- Tested cold Node/process caches and missing Redis documents. MySQL's buffer
  pool was **not** flushed; these are not cold-disk measurements. Network/CPU
  emulation is not a claim about a particular physical phone.

Page readiness requires visible content and hydrated controls. Run details
record content visibility and hydration separately. Tracker history is opened
through the actual profile Debug link. The local production Next server omits
the deployed nginx compression/cache layer, so raw resource bytes are not
production transfer sizes. See [the harness instructions](../../scripts/PERFORMANCE.md).

Range changes now select immediately, show pending feedback, preserve scroll,
and support keyboard and touch input. Intent prefetch is cancellable and
bounded rather than generating work for every visible leaderboard row.
The single Debug link retains automatic prefetch while its profile is visible.
Profile range and More runs timings remained effectively flat. The front-page
30-day and cached-return transitions were 73 ms and 22 ms slower in this
sequence; these measured regressions are retained in the table. Request counts
fell for range changes, but that is not evidence that every transition became
faster. The change favors bounded speculative work and immediate selected-range
feedback; further range-latency tuning remains possible.

The 100 ms hover timer is cancelled synchronously on mouse-down and does not
delay navigation. Baseline immediate hover can give its request a small head
start during an automated click. Final 30-day samples were 662.4, 566.2, and
639.6 ms, so one matched the baseline median; the slower cached-return sample
also contained a 60 ms browser long task. These observations do not establish
a fixed 73 ms application overhead.

The initial CSS experiment removed two render-blocking stylesheet requests.
It adds approximately 99 KB of raw initial HTML because CSS also appears in
Flight serialization: approximately 22 KB gzip or 10 KB Brotli in the isolated
comparison. The eliminated external CSS was approximately 51 KB raw. Subsequent
RSC range payloads were unchanged. `experimental.inlineCss` needs rechecking
after Next upgrades.

## Database and request work

History grids now filter, order, count, and paginate in MySQL instead of
retrieving and decoding a player's entire lifetime history. Only the requested
page is returned. The added `(uuid, lastUpdated, id)` index supports the normal
recent-first path. A projected timestamp alias initially defeated that index;
qualifying `pace.lastUpdated` removed the filesort. The actual captured query
plan reads 25 index entries rather than sorting 21,593 rows: roughly 28 ms
became 0.16–0.4 ms in the plan checks.

The index is installed locally. Deploy
[the idempotent index migration](../mysql/player-history-index.sql) separately
when releasing these commits. Arbitrary filters/sorts and deep OFFSET pages
can still examine more of a player's history.

Filtered personal bests use indexed lookups for the requested UUIDs instead of
materializing all players' PB documents. Identity, tooltip customization,
Twitch mappings, reset rates, and missing profile stats recover through scoped
queries. One player's cold lookup no longer enumerates the global dataset.

Three alternating fresh-process helper samples produced these medians. Heap
figures are measured deltas, not hard allocation limits. All six helper result

first-connection overhead into that board call. This is not a steady-state
Redis throughput comparison.

## Cold caches and bounded retention

- Missing compact leaderboard documents recover from generated root documents
  using bounded Redis prefixes, including average and conversion categories.
  A completely absent generated global dataset returns `503`,
  `CACHE_NOT_READY`, `Retry-After`, and `no-store`; the page offers Retry.
  Requests do not synchronously rebuild every player's historical stats.
- Cold profiles still render through player-scoped SQL. Their calculated
  values match independently produced cache values. Unavailable global ranks
  are represented by `-1` and hidden. Missing reset data is not shown as a
  fabricated zero. Injected compact-Redis read failure also preserves tooltip
  SQL fallback.
- The process data cache enforces default limits of 25,000 array rows per
  entry, 250,000 aggregate retained rows, and 2,000 keys. Nested arrays count
  toward the budget; eviction, expiration, flush, and concurrent request
  deduplication are tested. These are retention budgets, not exact byte caps.
- API endpoints reject malformed or oversized requests before fetching data.
  Expensive operations have bounded batch sizes and concurrent work, returning
  a retryable response when saturated. These caps are process-local; they are
  not a distributed rate limiter.

## Cache generation and memory

Cold aggregate scans now use backpressured, UUID-ordered batches and release
raw state after each player. History and combined buckets share a bounded
stream. Reset-rate reduction also releases per-player values rather than
retaining every player's raw rows. Consumer failures close the stream and
release the database connection.

Read-only comparisons checked exact aggregate hashes:

| Workload | Before elapsed / peak RSS | After elapsed / peak RSS |
| --- | ---: | ---: |
| Full pace aggregation, 2.98M rows | 6.32 s / 357.4 MiB | 5.10 s / 252.6 MiB |
| Full player histories | 4.02 s / 638.0 MiB | 4.78 s / 271.1 MiB |
| Reset-rate aggregation, 2.34M joined rows | 4.34 s / 286.6 MiB | 6.06 s / 204.5 MiB |
| Largest combined bucket, 137,760 rows | 307 ms / 198.3 MiB | 256 ms / 137.8 MiB |

History and reset-rate streams deliberately trade some elapsed time for lower
memory. They retain one player's raw arrays and compact summaries; an unusually
large single player can still increase memory use.

Actual publishing runs also passed:

- A forced full producer with pacing disabled completed in 10.97 s with
  311.1 MiB maximum RSS; all 8,422 generated values were byte-identical.
- Default-paced history/combined generation completed in 16.64 s with
  283.9 MiB maximum RSS; all 4,350 histories matched.
- Normal 1/7/30-day refresh completed in 9.31 s. The subsequent incremental
  history pass completed in 33 ms with no changed histories.
- An earlier default-paced full run took 331.3 s and retained identical output.
  Full jobs can take minutes by design. Pacing defaults are configurable;
  recent-history batches default to a 10 ms pause.

Average CPU during default-paced work was approximately 2–3% of one core, but
brief GC/processing samples still reached 119–136% in one-core units. The
changes reduce sustained work and memory; they do **not** eliminate CPU spikes.

## Frontend work

- Player search reuses its Fuse index, avoids unused match/score work, and
  cancels obsolete requests. Eight alternating samples over all 4,350 players
  and 12 queries had identical results and a 60.1 → 33.2 ms median (-44.9%).
- Historical run cards render the server snapshot immediately and use an
  isolated per-route store. They no longer wait for a browser `getWorld`
  waterfall or poll historical runs. Live runs refresh the compact same-origin
  endpoint, including when initialized from the server snapshot.
- Relative timestamps share a visibility-aware clock: 200 subscribers use one
  interval, hidden pages use none, and cleanup leaves none. Responsive content
  no longer creates duplicate mobile/desktop timers.
- Tracker rows share delegated pointer/focus/keyboard navigation handlers.
  Stationary pointers do not trigger prefetch on mount. Prefetch bookkeeping
  is capped at 64 entries with a 30-second lifetime.
- Session pages render all five cards with the correct data shape and remove
  unused live/Twitch lookups. OBS previews use ResizeObserver rather than
  polling layout every 20 ms; ordinary overlays install no size polling.
- Tiny run-card images use direct, low-priority resources with explicit
  dimensions, avoiding image-optimizer CPU and unwanted preload work.
  Front/profile/run screenshots and computed layout checks preserved geometry.

- Thirteen API early-validation cases, concurrency saturation/release, and

- Browser range keyboard/touch/pending behavior; intent prefetch; Debug-route

  across Back/Forward; tracker keyboard navigation; session cards; OBS resize;
