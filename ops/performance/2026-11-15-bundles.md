The server-page audit found that the main/profile/session data reads already
run in parallel where their inputs are independent. Resolving a name before
reading UUID-specific data is a real dependency, and metadata/page requests
already coalesce their shared reads. This round does not claim a new benefit
from simply rewriting those existing `Promise.all` calls. Run-page props also
reuse the same initial-world object; repeated prop references alone do not
prove duplicate RSC serialization.

## History reads and serialized rows

The normal history page needs one player's color and identity seed. It formerly
read the global customization projection, then searched that collection for
the player. It now calls the existing scoped `getUserInfo(uuid)` while the
initial run page loads in parallel. The cold Redis fixture rejects any
unscoped `users` query, checks the indexed `WHERE uuid=? LIMIT 1` read, and
compares the rendered player-info seed with the previous global result.

AA history still renders 100 rows initially and fetches 100 older rows per
Load more action. Its public API, cursor behavior, sorting/order and displayed
values are unchanged. Initial rows now contain only an ID, timestamp, live
flag and eight formatted cells. Unused fields and repeated split-property
names no longer cross that client boundary. Later raw API responses are
projected once before appending them, so rerendering existing rows does not
format their cells again. Cancellation, duplicate-click guards, player-change
isolation and failed-request retry remain intact.

Read-only checks use actual local AA rows for CroProYT:

| Rows | Raw props | Compact props | Raw props, Brotli | Compact props, Brotli | Rendered HTML |
|---|---:|---:|---:|---:|---:|
| 100 | 19,390 B | 8,995 B | 1,778 B | 1,266 B | 23,177 B |
| 200 | 38,715 B | 17,782 B | 3,191 B | 2,312 B | 45,698 B |

For 100 rows the JSON props shrink 53.6%, or 28.8% when compressed alone with
Brotli. Both row counts render byte-identical HTML against the frozen baseline
component, including headers, timers, live indicators, cells and controls.
The HTML SHA-256 values are
`67bdec8863af8d2bad25299319654865c5b2da155f720f0d4f6bb63615f9feef`
and `81f7c8697d3c0d86f52a50ffc1564bc2180c643497a1014059389820191379c3`.
These are prop-fragment and SSR checks, not an assertion that the complete
document or its production compressed response shrinks by the same percentage.
The final page probe measures the full document separately.

## CSS loading and static documentation

Player/profile styles now belong to the player layout; normal and AA history
styles belong to its history layout. OBS setup styles load on the setup page.
Shared table, navigation and timestamp-tooltip styles remain global, and
browser-source overlay styles retain their existing route behavior.

CSS extraction changes cascade order as well as payload scope. Review found a
specific conflict: `.openHistory button` could load after the equal-weight
`.ccOpenHistory button` and override its custom background. The fix targets
the combined classes, including hover, so custom colors retain their previous
priority. The style suite checks this with deterministic customization values.

Smaller initial global CSS can create a later route-specific stylesheet
request during client navigation. With inline initial CSS, a direct cold page
load and a cold front-to-profile click exercise different loading paths.
Immediate-click navigation traces and computed-style checks therefore matter
alongside front-page byte savings; the report does not assume CSS splitting
improves every transition.

The API documentation has no page-level interactive handlers. Removing its
client boundary avoids its page-specific client module and hydration work;
the shared navigation/search still hydrates. Server-rendering that markup also
changes the HTML/RSC representation. Complete document and script sizes must be
considered together rather than treating the removed client chunk as a net
transfer saving by itself.

## OBS controls and telemetry scheduling

The OBS color picker/input are visible controls. Their module is now part of
the route's initial JavaScript rather than a required script discovered after
hydration. In an isolated production build comparison, the old route plus its
later color chunk totals 32,456 raw bytes / 10,380 Brotli bytes; the combined
candidate is 28,607 raw / 9,061 Brotli bytes. The removed later request is about
9.8 KB raw. These numbers describe the isolated route/control bundle study,
not every byte downloaded by an OBS page. Final request and whole-page
measurements below determine the observed end-to-end effect.

Telemetry remains enabled with the existing production DSN and 10% trace
sampling. Its regular initializer still waits for load, three seconds, then
idle time; real early errors request the SDK immediately. The first router
transition no longer starts a competing SDK download. A shared browser bridge
keeps at most 20 pending error values, coalesces the loader, and gives the global
error boundary the same owner. Failed imports are caught, their promise can be
retried by a later error/idle attempt, and pending errors remain bounded.

Pre-initialization router transitions are intentionally dropped rather than
replayed. The installed SDK's `captureRouterTransitionStart(href,type)` starts
spans at call time and accepts no original timestamp. Replaying completed
transitions after initialization would fabricate new traces for old routes.
After initialization, transitions forward immediately to the SDK. Early
navigation tracing is consequently unavailable until the deferred SDK is ready;
error capture and subsequent tracing remain enabled.

The supported Sentry debug-log stripping option saves only 164 raw bytes / 12
Brotli bytes in the isolated build. That is a small result, not a large SDK
reduction. Build inspection found two entrypoint-specific SDK versions; it
did not establish that ordinary App Router visits download both. No duplicate
SDK byte-saving claim is made. The useful change here is when required work
starts, with one error-reporting owner and bounded early queues.

Local browser probes block external ingest/other third-party requests while
allowing same-origin application chunks. This test routing does not change
production telemetry configuration or disable the SDK's initialization.

[JSON](../../test-artifacts/performance/bundles/payloads.json) and
[log](../../test-artifacts/performance/bundles/payloads.log) contain script totals
and compression estimates. Raw document values below use the median of the three
paired browser samples in [pages.json](../../test-artifacts/performance/bundles/pages.json):

|---|---:|---:|---:|
| Front | 237,774 → 218,726 B | 8.0% | 22,385 → 20,292 B |
| NoFearr1337 profile | 128,324 → 114,962 B | 10.4% | 17,548 → 16,116 B |
| NoFearr1337 run history | 148,561 → 142,972 B | 3.8% | 17,801 → 17,278 B |
| CroProYT AA history | 164,435 → 148,327 B | 9.8% | 19,274 → 18,127 B |
| OBS setup | 117,344 → 105,361 B | 10.2% | 15,159 → 13,974 B |
| API documentation | 124,195 → 122,397 B | 1.4% | 16,777 → 15,909 B |

Both probes read complete responses, including inline CSS and RSC content.
Compression estimates are from the separate document snapshot, not the exact
median browser response. Live values and streamed response details can change
between captures; the exact AA cell/SSR parity fixture above supplies a separate

| Page | Declared modern scripts baseline → final | Declared JS, raw baseline → final | Declared JS, Brotli 5 baseline → final |
|---|---:|---:|---:|

The shared loader/error-bridge changes add a net 426 raw bytes to the common
declared scripts. AA's smaller route module offsets that increase, leaving its
declared JS 108 raw bytes smaller; its compressed total is 213 bytes larger.
API documentation removes its 7,632-byte page module, saving a net 7,206 raw
bytes / 2,492 Brotli-estimate bytes across declared scripts and one request.

OBS setup deliberately declares more JS initially so its visible controls need
no later module request. The baseline additionally downloads the 9,839-byte
color module after hydration, outside this declared-script table. Including
that required module, the final build's corresponding script total is
558,400 → 555,033 raw bytes, a 3,367-byte reduction, with the sequential
post-hydration download removed. This is distinct from the isolated bundle
comparison above.

Brotli 5 values are offline compression estimates, summed per individual
script response. They are not measured production wire transfer. These tables
exclude fonts, images, client-navigation RSC responses and subsequent dynamic
or idle scripts, including the later telemetry SDK. They therefore describe
complete initial HTML and its declared scripts, not all eventual page traffic.

## Verification and measurement method

The production build and full TypeScript check pass. Full ESLint has zero
errors and 47 existing warnings. Focused checks cover the scoped customization
query, AA row/cell/SSR parity, the existing AA loading/cancellation/retry paths,
OBS color-frame behavior and telemetry load/error/failure scheduling. No
stored SQL runs are created or deleted by the fixtures.

[The browser probe](../../scripts/perf-bundles.mjs) measures six actual local production paths: the front
page, a normal profile, normal run history, AA run history, OBS setup and API
documentation. Fresh Chromium contexts alternate baseline/candidate ordering
across rounds. HTTP uses 300 ms simulated latency, 10/5 Mbps throughput and
4× CPU slowdown. Third-party images are stubbed and other external browser
requests are blocked identically.

Content readiness means the expected content is visible; interactivity means
the relevant control/row carries hydrated React props. Measurements also
record request initiators, document and inline-style bytes, completed script
bytes, long tasks and LCP observed by that point. Assets are observed at
initial interactivity, not through every later idle download. Direct local
Next HTTP is uncompressed: decoded byte totals are not deployed Brotli/gzip
transfer sizes. The separately compressed fragment/bundle numbers above do
not substitute for a production proxy measurement. Browser contexts are cold;
that does not imply cold disk, MySQL buffers or every server cache.

With the archived baseline and final production servers already running in
Docker, open `docker exec -it -w /app pacestats-dev bash`, then run these probes
separately from builds and other profiling:

```sh
export PERF_BASELINE_URL=http://127.0.0.1:5101/stats/
export PERF_BASE_URL=http://127.0.0.1:5102/stats/
PERF_ROUNDS=3 node scripts/perf-bundles.mjs
node scripts/perf-document-payloads.mjs
```

The default outputs are
[pages.json](../../test-artifacts/performance/bundles/pages.json) and
[payloads.json](../../test-artifacts/performance/bundles/payloads.json).
The browser probe observes readiness and completed resources at that point;
the document probe independently waits for each entire HTML response and
counts modern declared script assets. Neither starts a production server.

## Paired cold-browser results

The primary run comprises 36 fresh contexts: three per revision for each of six
paths, with baseline/candidate order alternating. No browser errors were
recorded. The medians from [pages.json](../../test-artifacts/performance/bundles/pages.json)
and [pages.log](../../test-artifacts/performance/bundles/pages.log) are:

| Page | Content ready, baseline → final | Interactive, baseline → final | Local requests at interactivity, baseline → final |
|---|---:|---:|---:|
| Front | 753.3 → 749.7 ms | 1,345.8 → 1,347.4 ms | 13 → 13 |
| Profile | 498.7 → 493.4 ms | 1,353.9 → 1,354.4 ms | 12 → 12 |
| Run history | 513.2 → 521.1 ms | 1,379.2 → 1,354.0 ms | 11 → 11 |
| AA history | 529.0 → 516.9 ms | 1,257.6 → 1,257.6 ms | 10 → 10 |
| OBS setup | 469.1 → 449.9 ms | 1,753.5 → 1,424.0 ms | 15 → 14 |
| API documentation | 486.6 → 476.4 ms | 1,200.6 → 1,204.9 ms | 10 → 10 |

The clear readiness improvement is OBS setup: 329.5 ms, or 18.8%, earlier
interactivity, consistent with removing its sequential color-module download
under 300 ms latency. All other interactivity differences are 25.2 ms or less
and do not establish a meaningful speedup with three samples. Smaller
HTML and bounded backend/client work are retained benefits without claiming
all pages became visibly faster. This fixture is not a CPU or memory ceiling
measurement.

Front-page inline styles shrink from 52,396 to 42,873 raw bytes (18.2%). The
baseline already has zero render-blocking stylesheet requests in this initial
load trace; all 36 contexts retain zero such requests. CSS scope saves inline
document bytes here, not an existing blocking CSS round trip. Completed
resource counts can also miss a script still in flight: API's complete declared
script inventory above establishes its removed page module, whereas the
interactivity snapshot records ten local requests for both revisions.

## Navigation order and production parity

The production [CSS/navigation fixture](../../tests/route-css-parity.mjs),
committed as `050a79d`, passes 12 computed-style cases: front, AA leaderboard,
profile, normal history, AA history and OBS setup at widths 1,440 and 390 px.
It exercises filters, the mobile drawer, selected OBS previews and deterministic
custom colors, including normal/hover history buttons. Its 12 client-navigation
steps also pass across both revisions, with no browser errors. Detailed styles
and request traces are retained in
[route-css-parity.json](../../test-artifacts/performance/bundles/route-css-parity.json)
and its [log](../../test-artifacts/performance/bundles/route-css-parity.log).

Cold immediate clicks do discover route CSS after the RSC response, alongside
the already-required route JS. In the candidate front-to-profile trace, CSS
runs approximately 351–659 ms after the click while route JS runs 356–683 ms.
In profile-to-history, CSS runs approximately 352–662 ms and route JS
355–681 ms. The added stylesheet requests share that existing dependency phase;
these traces show no additional sequential CSS-only phase. The parity fixture
waits 100 ms while stabilizing computed styles, so its reported ready times
are diagnostic and are not the paired readiness benchmark above. Styles remain
cached on return navigation.

The actual production SDK fixture (`806e01f`) verifies that the first ordinary
navigation starts no SDK download; the first SDK request begins 3,010 ms after
load. A real early error instead starts it after 2 ms. It verifies one stable
SDK client, removed temporary error/rejection handlers, drained pending errors,
post-initialization navigation spans, 10% trace sampling and `debug=false`.
Captured error envelopes are observed while outbound ingest is blocked locally;
no unhandled rejection loop occurs. Evidence is retained in
[sentry-production.json](../../test-artifacts/performance/bundles/sentry-production.json)
and its [log](../../test-artifacts/performance/bundles/sentry-production.log).

## Complete front/profile navigation journey

A separate solo run performs the existing full navigation journey three times
per revision, alternating order. All 15 steps complete in all six contexts
(90 checks), with no browser errors. The
[step-indexed summary](../../test-artifacts/performance/bundles/navigation-summary.json)
retains all medians; individual `navigation-baseline-{0..2}.json` and
`navigation-final-{0..2}.json` files retain request and task details. Indexing
matters because the first 7-day selection and its later cached revisit are
distinct steps.

| Front, first 7 days | 559.9 → 552.5 ms |

| Runs, next page | 63.2 → 64.6 ms |
| Recent run detail | 795.7 → 802.4 ms |

Cold-front and first-profile readiness remain effectively unchanged. Range
changes and subsequent links show small differences in both directions,
including a 24.4 ms slower profile 7-day sample median. These results do not
establish a broad navigation latency win. First profile navigation records
four → six completed local requests, while its new route assets run in the
parallel phase described above; its median readiness remains flat.

Deferred telemetry work still costs CPU later. This journey observes an
85 ms long task on the baseline front 7-day step and a 66 ms task on the
candidate profile 24-hour step. Those observations are not reliable task
attribution or proof of a CPU reduction. Similarly, the run-detail step's
completed-script total changes from 278,807 to 32,515 bytes because SDK
downloads finish during different steps. That difference is not a reduced
run-detail bundle or missing route data. No lower CPU/RAM ceiling or removal
of the eventual SDK cost is claimed.
