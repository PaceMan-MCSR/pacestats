# OBS data delivery — 15 November 2026

OBS overlays now receive compact data snapshots over their WebSocket. Dedicated
browser-source pages seed their initial values into server-rendered HTML,
while embedded previews without a seed receive the first value over the socket.
A healthy overlay no longer receives a refresh instruction
and then makes a browser API request to obtain its new value. This applies to
session split counts, session nethers/NPH, combined split counts, and combined
nethers. Existing browser-source URLs and public API response shapes remain
compatible.

## Data path

```text
Committed stats insert / deletion, or existing Redis publisher
  → Redis UUID notification
  → WS event coalescing
  → affected active overlay parameter groups
  → one authenticated internal Next.js snapshot request per group
  → existing scoped SQL / combined summary and SQL-tail helpers
  → one serialized snapshot shared with matching viewers
  → browser applies the data without a browser API refetch
```

The socket service still uses HTTP internally. It calls
`http://127.0.0.1:5050/stats/api/obsSnapshot/` by default, with the private
`WS_TOKEN` in an Authorization Bearer header. Next.js owns aggregation and
database access; the WS process does not acquire its own SQL connections. This
removes the extra browser request and shares aggregation across viewers while
keeping one implementation of the session and combined statistics rules.

The internal response is `{data, uuids}`. The server uses authoritative UUIDs
to index the active groups affected by a notification; the browser receives
`{type:"snapshot", version:1, sequence, data}`. Responses and frames are bounded
and snapshots replace earlier queued snapshots. `reloadPage` retains priority.

Dedicated live browser-source pages also call this same server helper directly
when rendering HTML. This displays the first value without waiting for
hydration, a socket handshake and its first frame. It does not expose a
credential or make an internal HTTP request during SSR. Matching initial page
loads share in-flight work; a two-second LRU seed cache holds at most 64 values,
or roughly 2 MiB of serialized UTF-8 data at the snapshot-size bound. Objects
and runtime overhead consume additional heap. There are at most four distinct
pending seed reads, and both SSR and provider reads share one process-global
four-read budget even when Next.js creates separate module instances. Failed
or overloaded SSR seeds return no seed and retain the ordinary socket path.
Live snapshots never read this short seed cache and remain fresh after events.
Demo pages skip SSR aggregation and retain their one HTTP request.

An SSR seed also records when its authoritative read completed. The live
subscription sends that time as a `since` freshness hint. It is a per-viewer
minimum, not part of the parameter-group key, so it does not split matching
viewers into separate groups. The broker does not deliver a retained or
already in-flight result older than that viewer's HTML seed; it requests one
coalesced fresh read when needed. Matching pages reusing the two-second seed
also reuse its timestamp. This prevents the first live message from replacing
newly rendered HTML with an older snapshot while preserving shared reads.

A parameter group includes the overlay type and its data settings. Browser
overlays with the same canonical subscription URL and freshness hint share a
socket. The server excludes that hint from its group key, so viewers with
different seed times still share aggregation for the same data variant within
each WS process. Different types or session settings require different subscriptions;
an OBS setup page displaying two different overlays can use two sockets. There
is no claim of one socket for every overlay on a page or one group shared
across separate WS processes.

## Freshness, limits and resource use

The internal endpoint authenticates before SQL, Redis, rate-limit allocation
or concurrency accounting. It returns `private, no-store` and calls fresh
helpers. Session split snapshots bypass the nested 20-second row cache as well
as the public 10-second result cache. Nether snapshots bypass the public
five-second row/NPH caches. Name and alias resolution remains cached; it does
not have to enumerate player history on each notification. Combined snapshots
retain their existing summary-version/staleness checks and authoritative SQL
tail or fallback reads.

| Bound | Default behavior |
|---|---|
| Active parameter groups | At most 512 per WS process. Only active groups retain a latest snapshot. |
| Viewers per parameter group | At most 100. Existing total-client and socket-backpressure limits also apply. |
| Internal fetch concurrency | Two per WS process, with a bounded pending group set. |
| Next.js snapshot concurrency | Four per Next.js process shared by SSR and the internal provider, including identity and aggregation work. |
| Snapshot size | At most 32 KiB for the internal body and outgoing frame; oversized streamed bodies are cancelled. |
| Delivery callback | At most 256 queued client sends before yielding. A newer queued snapshot replaces an older one. |
| Quiet-group refresh | Every 30 seconds after a successful read, through the same bounded queue. |
| Provider outage | Five-second group retry delay; eight-second internal request timeout. |
| Idle cleanup | Last-viewer removal deletes group/index entries, cancels queued work, aborts the in-flight fetch and releases its retained snapshot. |

The 512 × 32 KiB bound permits about 16 MiB of serialized UTF-8 data for the
latest active-group messages. It is not a JavaScript-heap or process-RAM limit:
strings, maps/sets, queued deliveries, socket buffers, JSON parsing and SQL
working rows use additional memory. Aborting an HTTP request does not imply an
already executing MySQL statement stops immediately. Existing database query
and pool limits still apply. The larger nether projection can read up to
100,000 rows for an unusual long session; no global CPU or RAM ceiling is
claimed.

One UUID event refreshes only affected groups, including combined overlays
containing that player. Repeated notifications share pending work. Notifications
that arrive during a read request one following read so a newly committed
update is not lost behind the in-flight result. Initial name-resolution/event
races are checked conservatively as well.

The 30-second refresh is still necessary: rolling windows can expire without
an incoming event, and some pace writers do not publish through this service.
It moves this work from a timer in every viewer to one job per active variant.
Joining an already loaded group reuses its last snapshot when it meets that
viewer's freshness minimum. A viewer with a newer SSR seed instead requests a
shared fresh read; joining can therefore cause additional work. During an
outage, the last successful value stays visible.

Session nethers preserve the existing larger public run cap; session split and
NPH helpers preserve their existing caps and truncation behavior. The work is
bounded per request, rather than claiming that every requested lifetime can be
computed cheaply. An overlay configured with `nph=false` does not execute the
additional NPH tracker query: a nonempty short session uses one SQL read
instead of two. Its hidden `rnph` field is zero; the public API and overlays
requesting NPH retain their existing RNPH values.

Successful stats inserts publish after the authoritative write. Successful
run deletions now publish after their transaction commits as well. Duplicate
inserts, failed writes and rolled-back deletions do not emit a successful
refresh. Optional Redis publication failures preserve a committed write's
success; periodic shared reads and browser recovery remain available.

## Browser recovery and compatibility

Healthy pushed snapshots update SWR directly with revalidation disabled.
Browser interval, focus and online revalidation do not fetch behind that live
stream. Version and sequence checks reject old or invalid frames, and changing
player/settings isolates the new subscription from old results. Reconnection
resets sequence tracking for the new stream. A pushed value also fences an
older in-flight HTTP fallback response so it cannot overwrite newer data.

Unavailable sockets, a ten-second initial stream timeout, provider errors and a stale
stream enable the existing public API recovery path. Reconnection and HTTP
retries use bounded backoff/jitter; 429/503 responses preserve the last good
value. Each fallback fetch has a ten-second timeout. Recovery requests for
matching overlays in one browser share in-flight work. Successful pushed data
stops polling again. The public fallback retains
its existing cache semantics, so it does not have the internal fresh-read
guarantee during an outage. Demo previews fetch once through HTTP and create
no socket or background polling loop.

Legacy `/pull/{uuid}` clients still receive their existing bare `refresh` or
`reloadPage` messages. Authenticated `/push/{uuid}/{token}` calls and Redis
publishers remain supported. Deploy the Next.js snapshot endpoint before the
new WS service, with matching private `WS_TOKEN` values. Set
`WS_SNAPSHOT_ENDPOINT` to the direct Next.js URL with its trailing slash;
redirects are intentionally rejected. Proxies must forward the new `/overlay`
path alongside legacy paths. New overlays connecting to an older WS service
fall back to HTTP; reload those OBS browser sources after upgrading WS to
establish their data subscriptions. `NEXT_PUBLIC_WS_ENDPOINT` changes require
a production site rebuild.

Production verification caught a URL compatibility issue before completion:
Next.js dynamic route parameters can still contain `%2C` for a combined-player
comma. The four components now decode names once and then quote them as query
values, avoiding double-escaped names in both API recovery and socket URLs.
Both literal-comma and escaped-comma combined browser-source paths are covered.
The internal provider URL also uses the canonical trailing slash; the real
production check verifies it returns data directly rather than a redirect.

## Verification

All application, database and browser checks run in the local Docker
environment. Backend fixtures replace SQL execution where mutations or changing
rows are needed; they do not insert/delete stored runs. Read-only parity checks
use the actual local MySQL/Redis dataset and frozen pre-change public routes.

- `tests/obs-snapshot-data.ts` warms public caches with one fixture run, then
  changes the fixture to two runs. Fresh helpers immediately return two while
  ordinary public helpers retain their cached value. It also checks formatting,
  live-only predicates, empty results, zero identity queries and the hidden-NPH
  query skip.
- `tests/obs-snapshot-route.ts` checks authentication before work, 13 invalid
  parameter cases with zero SQL/Redis work, all four kinds, nickname/Twitch
  resolution, unknown users, the four-read cap, released slots after failure,
  retry headers and the 32 KiB response cap.
- `tests/obs-snapshot-shared-budget.ts` loads an independent copy of the server
  helper, as separate Next.js bundles can. SSR calls, that second module and
  the authenticated route share the four-read process cap. The fixture checks
  exact SSR/provider data, validation before work, authentication before the
  occupied budget, 429 responses, and released slots after success/failure.
- `tests/overlay-initial-data.ts` checks demo bypass, simultaneous read sharing,
  the exact two-second TTL and 64-entry LRU, pending-read overload, uncached
  failures and oversized responses, live-provider cache bypass, and encoded/raw
  combined-player names. Seed completion times survive cache reuse and are
  passed as freshness hints. The final client/WS fixtures also cover preventing
  older retained/in-flight snapshots from replacing a newer seed.
- `tests/obs-snapshot-parity.ts` compares 11 snapshot responses and 11 current
  public responses with frozen public API results. Short/lifetime windows,
  session gaps, live-only, decimal precision, duplicate combined names, start
  and maximum-time filters match exactly. Snapshot bodies in these cases are
  122–462 bytes; these are sampled response sizes, not a universal maximum.
- `tests/obs-mutation-notifications.ts` verifies commit-before-publish ordering,
  duplicate/rollback suppression and Redis failure behavior without stored
  writes. Existing session-boundary and API-bound fixtures also pass.
- `tests/websocket-snapshots.mjs` checks canonical parameter keys, bounded
  concurrency/groups/clients/body buffering/fanout, UUID isolation, rolling
  freshness, event/read/reload races, outage backoff, cancellation and idle
  cleanup with deterministic clocks and providers.
- `tests/websocket-snapshot-delivery.mjs` uses 30 real WS clients, actual local
  Redis Pub/Sub and a private counting HTTP provider. Thirty matching viewers
  cause one initial backend request. A coalesced burst causes one request per
  affected parameter variant, with the same serialized response sent to every
  matching viewer. Other UUIDs remain isolated; combined membership, legacy
  delivery, reload ordering and outage backoff are checked. This isolates
  request sharing; its HTTP response is a fixture, not a SQL timing result.
- `tests/overlay-client-delivery.mjs` mounts the four real overlay components
  with React/SWR in Chromium. Five mounted overlays with one identical pair
  use four sockets and zero initial browser API requests. Pushed values update
  visible output. Advancing 70 seconds and firing focus/online events causes
  zero healthy-stream API reads. The fixture also verifies malformed/old
  frames, settings isolation, late-HTTP fencing, 503/429 recovery, demo and
  legacy behavior, and sequence reset after reconnect.
- `tests/overlay-production-parity.mjs` opens 28 actual production pages:
  baseline and candidate, live and demo, across seven overlay/player/settings
  cases. All four types, two individual players, combined players, NPH on/off,
  decimal precision 1/3, and literal/escaped comma paths preserve rendered
  values and styles. Live candidates use the real broker with zero browser API
  requests; their raw initial HTML already contains the correct values before
  client requests or socket setup. Each demo fetches once. Protected
  endpoint authentication, no-store/no-redirect behavior and public API values
  also pass. The test reports 14 paired cases, each with two page revisions,
  with no browser runtime errors.

The complete TypeScript check passes. Full ESLint reports zero errors and 47
existing warnings; owned backend checks are clean. The complete new backend,
mutation and WS validation chain passes in
`test-artifacts/performance/obs-live/node-validation.log`. Fixture counts
and the 30-viewer request reduction demonstrate work elimination and bounds;
they do not establish a general CPU/RSS percentage reduction. Active variant
count and the largest requested player's data still determine aggregation
cost. A WS process now performs shared reads even when a single viewer is
connected. Quiet session-nether refreshes change from each viewer's old
60-second API interval to each active variant's 30-second fresh read. Quiet
combined-nether refreshes change from 20 to 30 seconds, so an expiration or
unnotified external change can appear later in that case; shared event
notifications still trigger updates promptly. Fresh reads also perform work
that an old short-lived API cache could previously reuse during repeated
updates. Under many matching viewers that work is amortized; many different
variants still consume separate work. These are deliberate freshness and
sharing tradeoffs, not claims that every single-viewer configuration uses less
SQL or displays its initial value faster.

SSR seed data can be up to two seconds old when a matching page-load burst
reuses it; the first live snapshot still uses the fresh path. A cold page load
can perform an SSR aggregation and a later initial WS aggregation. The short
seed cache and in-flight sharing reduce duplicate page-load work, but it is
not shared with live updates. SSR also moves its data-read latency before the
initial page response; slow data reads can delay HTML. Overload and read
failure omit the seed rather than adding an error page, leaving socket/API
recovery available. These bounds and fallbacks are the safeguards; there is
no claim that server-rendering every cold lifetime request is free.

An additional local Next.js process uses empty Redis database 15 to check

## Production data-arrival measurements

The session-nethers comparison uses the actual production Next.js overlay and API,
actual WS services and local SQL/Redis. `scripts/perf-overlay-updates.mjs`
alternates three fresh browser contexts per revision and sends three isolated
Pub/Sub notifications per context. HTTP receives 300 ms simulated latency,
10/5 Mbps throughput and 4× CPU slowdown. Real socket frames are explicitly
relayed with 150 ms downlink delay because CDP HTTP throttling alone does not
model WebSocket frame latency. Both local revisions use the same data.

The dataset is static: the probe measures data arrival after a notification,
not a changed-value DOM paint. It verifies that the baseline obtains data
through one browser API request per event, whereas the candidate receives a
snapshot and performs zero browser API requests for that event. The internal
WS-to-Next request remains part of candidate delivery time. These local
measurements exclude production proxy/TLS and remote database conditions.

Initial values in the page DOM are measured after `DOMContentLoaded` and a
positive count is present. This is not a paint, LCP or font-completion metric.
Readiness with both data and an open socket is measured separately. Requiring
the latter for the baseline would include its API-then-socket dependency and
overstate a first-DOM-data gain. The initial candidate snapshot is explicitly
drained before measuring events, so it cannot be mistaken for notification
delivery.

Final medians from `test-artifacts/performance/obs-live/update-delivery.json`:

| Metric | Baseline | Final | Change |
|---|---:|---:|---:|
| Initial values in page DOM | 1722.0 ms | 432.5 ms | −74.9% |
| Initial values and open socket | 2033.2 ms | 1890.7 ms | −7.0% |
| Notification to data arrival | 563.5 ms | 324.7 ms | −42.4% |
| Browser API requests per notification | 1 | 0 | One request removed |

There are three alternating fresh browser contexts per revision and three
events per context: nine data-arrival samples per revision, with no browser
runtime errors. Initial DOM/subscription medians each use three contexts per
revision. Events within a context are not independent cold starts. These
small controlled samples demonstrate the removed browser round trip under the
stated conditions, rather than statistical significance or a guarantee across
all players and networks. They do not measure a changed-value DOM paint.

An earlier socket-only initial-load diagnostic is retained as
`update-delivery-pre-ssr.json`, rather than reported as the final result. It
showed why the final version seeds dedicated pages in HTML. The final timing
file contains the SSR/freshness-guard version and isolates its initial frame
from later notification measurements.
