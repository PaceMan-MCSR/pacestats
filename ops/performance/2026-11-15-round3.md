and generated Redis data. Cron and producers were stopped during timing. Three

## Producer memory and exactness

Fixed timestamps make the 1d/7d/30d producer comparisons reproducible. Full
result hashes match the previous implementation, including SQL batches of
31 and 5,000 and an older timestamp with nonempty data in all three windows.

| Workload | Before → after |
|---|---|
| Pace windows, 75,023 rows | 324 → 252ms CPU; peak RSS 232 → 163MiB |
| NPH windows | 135 → 124ms CPU; peak RSS 163 → 129MiB |
| 150 busiest-player-sized history merges | Median CPU 202 → 128ms |
| 150 history relayouts, including UTF-8 encoding | Median CPU 243 → 110ms |
| 9,090 real summaries, repeated 30 times | Median CPU 218 → 205ms across seven alternating pairs |

NPH CPU is a modest, noisy improvement; streaming's clearer benefit is memory.
Another pace pair measured 214 → 180MiB peak RSS, so the 69MiB saving above is
not a universal constant. Of the real summaries, 4,123 (45%) have at most two
values and now avoid a typed array. All summaries match the numeric reference,
including NaN and signed-zero behavior.

Actual publishing passed too. The normal refresh produced all 1/7/30-day
documents and preserved the lifetime dataset's checksum. A complete recent-job
run published 6,562 history values from 2,982,052 rows and rebuilt combined
summaries from 2,948,864 rows. Comparing the published history against the frozen
baseline producer matched all 155,151,387 encoded body bytes after excluding
only the generation header on each head/base. Leases were released. These
integration jobs used zero pacing delay to finish promptly; ordinary producer
pacing remains in place. Their wall times are not used as comparative results.

## Cold requests and limits

A fresh-process, empty-Redis diagnostic burst sends 18 concurrent read-only
session, NPH, export, history, PB and latest-completion requests, followed by
two recovery requests. Both revisions returned 12 successful responses and six
retryable busy responses, then recovered. The final pair measured:

| Burst measure | Baseline | Candidate |
|---|---:|---:|
| Concurrent burst wall time | 550.0ms | 552.6ms |
| Next process CPU during burst | 730ms | 720ms |
| Starting Next RSS | 152.2MiB | 150.3MiB |
| Sampled peak Next RSS | 313.2MiB | 309.4MiB |

This whole-server burst is effectively unchanged, despite the narrower session
reads. First-load module initialization, multiple simultaneous exports and
JSON serialization are included. It is one diagnostic pair, not a benchmark
median, and network throttling applies to the separate browser measurements.

Both normal and empty-Redis HTTP suites pass. Empty global leaderboard data
continues to offer Retry and return retryable `503 CACHE_NOT_READY` API responses;
profiles, scoped history, identity and PB requests recover from SQL. No request
tries to rebuild the complete leaderboard dataset synchronously. MySQL buffers
were not flushed: cold tests mean a fresh application process and empty Redis,
not cold disk.

Request concurrency limits are process-local. RSS samples cover the Next
process only, not all container or database memory, and do not establish a
hard memory or CPU ceiling. Large exports and first-load module initialization
still allocate memory; occasional CPU/GC spikes remain possible.
