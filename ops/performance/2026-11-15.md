# PaceStats performance investigation — second round, 15 November 2026

This round compares the previous round's final commit, `edf658e`, with production
application commit `30eba7d`. `d5deec5` additionally fixes local dev hydration.
All work and testing used local Docker on `codex-perf`; nothing was pushed.
The [first report](2026-11-14.md) describes the earlier changes and remaining
limits. Results here compare against that already optimized version.

## Browser measurements

Three alternating baseline/final Chromium runs used 300 ms network latency,
10/5 Mbps bandwidth and 4× CPU slowdown. Every run used a fresh browser context
with HTTP caching disabled; Next router reuse remained enabled. Browser API and
telemetry requests outside Docker were blocked, and external avatars were
stubbed. Both production builds used the same dependencies, webpack build
command, MySQL dataset and Redis generation. Cache producers and cron were
quiet during timing. Both servers were restarted after publishing verification
to remove stale process-cache differences.

Page readiness includes hydrated controls and a hydrated leaderboard link when
present. Run content and hydration are measured separately. Navigation uses
actual links and range controls. These simulate constrained execution; they
are not physical-phone measurements. MySQL's buffer pool was not cleared, and
local Next does not include production nginx compression.

| Action | Before | After | Change |
| --- | ---: | ---: | ---: |
| Front, hydrated controls | 1,348.8 ms | 1,375.2 ms | +2% |
| Front → 1 day | 477.5 ms | 471.6 ms | -1.2% |
| Front → 7 days | 616.5 ms | 538.9 ms | -12.6% |
| Front → 30 days | 621.6 ms | 514 ms | -17.3% |
| Front → lifetime | 698.6 ms | 578.5 ms | -17.2% |
| Front → cached 7 days | 192 ms | 171.9 ms | -10.5% |
| Open player profile | 881 ms | 914.6 ms | +3.8% |
| Profile → 1 day | 387.8 ms | 386.9 ms | -0.2% |
| Profile → 7 days | 394 ms | 396.4 ms | +0.6% |
| Profile → 30 days | 398.3 ms | 398.5 ms | +0.1% |

Run hydration measured 826.4 → 825.4 ms. Largest contentful paint measured
508 → 528 ms. Initial front readiness was 26 ms slower, opening a profile
34 ms slower, and cached Debug navigation 38 ms slower in these samples;
those outcomes are retained rather than described as across-the-board wins.
The large gains are range payload/transition cost, prepared history navigation
and opening the native filter controls.

| First filter interaction | Before | After |
| --- | ---: | ---: |
| First usable preset, three-run median | 893.3 ms | 92.5 ms |
| Additional script bytes on open | 208,392 B | 0 B |
| Additional requests on open | 3 | 0 |
| Browser heap after open, median | 7.32 MiB | 5.87 MiB |

The new filter form is only mounted when opened, but its small native control
module is bundled with the history route. An intermediate version retained
lazy loading: it removed most bytes yet still took about 900 ms to open because
script/stylesheet loading remained on the interaction path. The final version
removes that round trip. The history route pays for the small form module up
front; the front page does not load it.

## Smaller leaderboard updates

The previous front page serialized complete table element trees and hydrated
up to 140 separate link components. It now sends a compact model of only the
selected rows, with repeated player identities shared in a dictionary. One
client table renderer produces the same initial HTML and owns bounded delegated
navigation, hover/focus/touch prefetch and pending feedback.

Direct uncompressed HTTP checks against the same Redis data showed:

| Payload | Before | After | Reduction |
| --- | ---: | ---: | ---: |
| Front 30-day HTML | 312,750 B | 237,501 B | 24.1% |
| Front 30-day RSC navigation | 103,898 B | 38,507 B | 62.9% |
| Lifetime HTML | 309,940 B | 236,783 B | 23.6% |
| Lifetime RSC navigation | 103,837 B | 37,969 B | 63.4% |

These are raw payload sizes, not compressed production transfer sizes. Browser
parity checks compare visible values, headers, help text, colors, links and
avatar attributes across all ranges, four views, split modes and quantity
columns. Native modified/new-tab links, keyboard navigation, deliberate intent
prefetch, pointer sweeps and browser Back remain covered.

## Profile and history interactions

- Profiles fetch only the displayed player's customization. This mainly avoids
  a cold all-users read/projection; the warm customization list was already
  small, so the warm profile payload difference is modest.
- The single More runs destination is prepared while visible on normal and AA
  profiles after a cancellable 750 ms grace period; hover/focus/touch can prepare
  it earlier. It fetches one bounded first page, preserving pending feedback.
  Preparing immediately caused an intermediate regression for an immediate
  recent-run click, so the final version keeps speculative work out of that
  initial navigation. Run rows and large leaderboard lists retain bounded
  intent prefetch rather than automatic prefetch for every destination.
- Superseded history sort/filter/page fetches abort, preserving an in-flight
  next-page prefetch when it becomes current. Unmount aborts retained requests;
  aborted requests cannot remove a newer request's bookkeeping. Failures now
  offer Retry instead of silently leaving old rows without recovery.
- Native filter controls preserve presets, time thresholds, local dates,
  operators and reset behavior. Browser tests check API results, keyboard
  access, cancellation, newest-result rendering and failure recovery.
- Tooltips capture their anchor on interaction rather than setting state during
  mount. React delegates hover/focus events instead of installing four native
  listeners per trigger. A tracker with 107 triggers avoids 107 mount rerenders
  and 428 native listeners. Open tooltip placement is frame-coalesced on scroll
  and resize. Child handlers/refs and SVG help interactions remain covered.

## Database and cold API work

Ascending history sorts now select IDs through a narrow covering index before
fetching full run rows. For the busiest player (21,593 runs), finish ascending
went from approximately 55 ms for the wide-row sort to 6.5–7 ms. The change uses
existing indexes; this round adds no database migration. Date ascending also
uses late row materialization. Thirty-two correctness cases, NULL/tie ordering
and captured SQL plans pass.

Profile NPH, Twitch and customization readers share cached/in-flight reads.
A twenty-way isolated burst now performs three Redis JSON reads total:
one each for users, NPH and Twitch, instead of repeated reads/parsing per caller.
Cold named PB lookup resolves candidate UUIDs and validates current names through
targeted indexed queries, preserving exact-case and reused-name behavior.

Single fresh-process Docker comparisons (not three-run browser medians):

| Work | Before | After |
| --- | ---: | ---: |
| Cold named PB wall time | 126.8 ms | 52.8 ms |
| Cold named PB process CPU | 47.6 ms | 28.4 ms |
| Cold named PB heap growth | 14.1 MiB | 2.1 MiB |
| Cold AA fallback process CPU | 123.7 ms | 94.8 ms |
| Cold AA fallback heap growth | 19.4 MiB | 8.0 MiB |
| Cold AA fallback sampled RSS growth | 49.3 MiB | 22.5 MiB |

The AA fallback streams its 55,067 source rows into the existing numeric series
and player map rather than retaining all raw row objects or doing an
`includes` search per row. Full output hashes match the buffered implementation.
An injected row-consumer failure drains/releases the connection and a subsequent
query succeeds. Trimmed-average series themselves still retain values needed
for exact calculations; this is not a constant-memory algorithm.

MySQL prepared statements now default to at most 256 per connection instead of
the driver's 16,000. The ten-connection pool could otherwise retain more than
MySQL's global prepared-statement limit under varied query shapes. A real
96-query test with a configured limit of 32 verifies retention, server-side
statement closes, eviction and transparent re-preparation. Evicted statement
shapes can incur preparation work again; the cap favors bounded retention.

## Producer CPU and allocation

The 2,982,052-row pace scan computes numeric timestamps once per row, updates
name metadata as scalar fields, and avoids a new closure and latest-name object
for each row. Ordered pace/NPH scans reuse the current player's accumulator
instead of hashing the same UUID for every row. Unordered/short-period callers
retain a map-based path with explicit parity tests.

Read-only actual-row comparisons retained identical hashes for all 4,350 pace
and 4,068 NPH summaries:

| Work | Before | After |
| --- | ---: | ---: |
| Pace process CPU | 3,778–3,810 ms | 2,514 ms |
| Pace peak RSS | 255–258 MiB | 229 MiB |
| Pace observed GC time | 82–85 ms | 48 ms |
| NPH process CPU | 1,192 ms | 1,070 ms |

These are isolated producer samples, not whole-service CPU or memory limits.
Pace wall time remained database-dominated in the first pair (4.70 → 4.73 s).
The final pace sample observed 83 collections; the earlier metadata-only
experiment observed fewer, so the report does not use that intermediate count
as the final result. Brief CPU/GC spikes remain possible.

A faster CSV concatenation microbenchmark was rejected: its full producer
used more CPU and increased RSS from about 269 to 299 MiB. The existing history
encoder remains unchanged.

Actual local publishing also passed. A forced full rebuild generated 8,422
values; 8,421 were byte-identical to the earlier snapshot. One `rtanph` field
aged from 0.03 to 0.02 because the snapshots were eight hours apart. Restoring
only that field in memory reproduced the complete original checksum exactly.
Normal 1/7/30-day publishing exercised the map path, covered 73,932 thirty-day
rows and 16,909 dynamic keys, and preserved every lifetime value. Job leases
were released. Timing during this publishing check overlapped other validation
and is not used as a performance comparison.

## Local dev hydration

Next rejected HMR websocket upgrades with a `127.0.0.1` origin while accepting
`localhost`. Missing React debug-channel data prevented dev hydration despite
successful HTML and JavaScript responses. A narrow
`allowedDevOrigins: ['127.0.0.1']` setting fixes this. Docker browser checks now
verify front/profile/runs hydration, actual range changes and no HMR errors at
the harness's loopback address. Production behavior is unchanged.
