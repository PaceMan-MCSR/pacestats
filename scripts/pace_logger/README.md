# PaceMan run logger

## Single-file setup for jojoelog

For the existing `jojoelog` systemd service, copy **only `new.py`** to
`/root/jojoelog/new.py`, alongside the existing `.env`, and run as root:

```sh
python3 /root/jojoelog/new.py --install
```

This supports Python 3.10.12. It creates `/root/jojoelog/.new-venv`, installs
its own pinned dependencies, reads the existing service environment and `.env`,
and defaults to MySQL user `pace` and database `pace`. It prompts privately for
the MySQL password if the existing configuration does not contain it. A local
MySQL socket is detected if no database host was configured.

Setup checks the existing table before stopping `jojoelog`. It backs up the
database under `/root/jojoelog/backups/`, then applies only missing migration
steps. Existing duplicate run identities stop setup without deleting any rows.
It installs a service override pointing to the private interpreter and `new.py`,
reloads systemd, starts the service, and waits for the new process to report
successful database/outbox startup through systemd's native `Type=notify`
protocol. It also checks that the same process stays active for three seconds.
Startup does not depend on a readiness file or a wall-clock timestamp.
`WorkingDirectory` is emitted without literal quotes, including on systemd 249.
The existing `pacelogger.py` stays in place.
Afterward the normal control command is still:

```sh
systemctl restart jojoelog
journalctl -u jojoelog -n 50 --no-pager
```

Settings needed outside the original service environment are saved in a private
`.new-settings.json` file. Passwords are never passed in command arguments or
written into the service override. Normal service starts do not install packages
or run database migrations. Setup requires `systemctl`, MySQL client tools
(`mysqldump`), internet access for the first dependency installation, and Python
venv support (`python3.10-venv` on distributions that package it separately).
If an existing private environment is missing `pip`, `--install` repairs it in
place with `ensurepip`. On a root Debian/Ubuntu setup where the bootstrap support
is missing, it runs `apt-get update` and installs the matching versioned venv
package, such as `python3.10-venv`, then retries. Existing environment files are
kept. These repairs run before any database migration or service stop.

If setup fails after stopping an active service, it attempts to restore its
previous override/settings and restart it. Completed additive schema changes
and the backup remain in place; rerunning setup skips those completed changes.
If MySQL refuses ALTER privileges or duplicate
rows need reconciliation, the installer reports the issue rather than changing
permissions or deleting data automatically.

The single file is generated by `build_singlefile.py` from `pace_logger.py`,
`singlefile_bootstrap.py`, and `install.py`; those helper files are development
sources and do not need to be uploaded to the server.

## Logger implementation

`pace_logger.py` replaces the supplied server script with an asynchronous
receiver, a local durable outbox, and one MySQL writer. It keeps the existing
`pace` columns and their units while adding a source timestamp used to reject
older run updates.

The writer removes the per-message MySQL ping and existence count, uses one
atomic upsert per run, and commits up to 50 queued jobs together by default.
Event lists are indexed once per payload, and ARS snapshots use set comparison
instead of nested searches. These reduce round trips and repeated work; no
production throughput multiplier is claimed. Durable local writes add disk I/O
in exchange for recoverable database delivery.

Python 3.10 or newer is required, including Python 3.10.12. Run commands below
from the repository root. On Python 3.10, the pinned `async-timeout` backport
provides the timeout context manager introduced in Python 3.11. Network retry
handlers also catch Python 3.10's separate `asyncio.TimeoutError` exception.
The WebSocket dependency is pinned to 16.1.1, which supports Python 3.10.
Messages are received through the streaming API and bounded to 1 MiB and 4096
fragments before assembly. This avoids the fragment-accumulation issue described
in the upstream [WebSocket security changelog](https://websockets.readthedocs.io/en/stable/project/changelog.html).

## Install and validate

```sh
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
# Windows PowerShell instead:
# .\.venv\Scripts\Activate.ps1
python -m pip install -r scripts/pace_logger/requirements.txt
```

Use `env.example` in this directory as a configuration reference. Keep the
existing server environment variables:

| Variable | Purpose |
| --- | --- |
| `DB_HOST` | MySQL hostname |
| `DB_NAME` | Database containing `pace` |
| `DB_USERNAME` | MySQL account |
| `DB_PASSWORD` | MySQL password |
| `DB_PORT` | MySQL port; default `3306` |
| `DB_SSL_CA` | Optional CA file; enables certificate and hostname verification |
| `PACEMAN_WS_SERVER` | PaceMan WebSocket endpoint |
| `PACEMAN_WS_TOKEN` | Value sent in the WebSocket `auth` header |
| `TWITCH_CLIENT_ID` | Optional Twitch application ID |
| `TWITCH_CLIENT_SECRET` | Optional Twitch application secret |
| `ARS_URL` | Live-run polling endpoint; default `http://localhost:8001/api/ars/liveruns` |
| `PACE_SPOOL_PATH` | Persistent local SQLite outbox path |
| `HEARTBEAT_FILE` | File whose modification time indicates a successful pace write |
| `PACE_SPOOL_LIMIT` | Maximum queued durable jobs; default `100000` |
| `PACE_DB_BATCH_SIZE` | Maximum jobs per MySQL transaction; default `50` |
| `PACE_UPDATE_INTERVAL` | ARS poll interval in seconds; default `2` |
| `LOG_LEVEL` | Logging level; default `INFO` |

Twitch credentials are optional; set both or neither. Use absolute spool and
heartbeat paths under a service manager: relative paths resolve against the
process working directory. Connection and operation timeouts are fixed in the
script: MySQL connect 10 seconds, read/write 15 seconds, lock wait 10 seconds;
ARS total 10 seconds; WebSocket open 10 seconds and close 5 seconds; Twitch
lookup 8 seconds and close 5 seconds. Retry backoff has a 30-second base cap
with 20% jitter. These are bounded waits, not additional environment controls.

The database needs both of these schema changes before this version starts:

1. A unique index covering exactly `(worldId, uuid)`.
2. A `sourceLastUpdatedMs BIGINT` column for the incoming run timestamp.

Review `migration.sql` before applying it. The repository's schema dump has a
normal index named `uniquerun`; its name does **not** make it unique. The
replacement checks its actual index metadata and the timestamp column at
startup. It does not silently alter the production schema.

Back up the database and inspect duplicate `(worldId, uuid)` pairs before
adding the unique constraint. Resolve duplicates deliberately: other tables
may refer to a particular `pace.id`. Neither this logger nor its migration
automatically deletes or merges historical rows. Adding an index on a large
table also needs a suitable deployment window for the server's MySQL version
and workload.

After the reviewed migration and configuration are in place:

```sh
python scripts/pace_logger/pace_logger.py --env-file /path/to/.env --check
python scripts/pace_logger/pace_logger.py --env-file /path/to/.env
```

`--check` validates configuration and database compatibility without starting
the ingestion loops. Do not run this version alongside the original logger:
the original does not participate in the source-ordering rules.

## Persistence and recovery

The WebSocket receiver validates each update and commits it to SQLite before
the MySQL writer processes it. SQLite uses WAL mode with `synchronous=FULL`.
The MySQL writer drains committed jobs in FIFO order, uses bounded batches,
and acknowledges a batch locally only after its MySQL transaction commits.
Only one worker owns the MySQL connection; the receiver, ARS poller, and
optional Twitch lookups do not share it.

If MySQL becomes unavailable after startup validation, the local outbox retains
accepted updates while the writer reconnects with capped exponential backoff.
Initial database connectivity and schema verification must pass before network
ingestion starts; use a service supervisor to restart a failed startup.
If MySQL committed a batch
but the process crashed before the local acknowledgement, the batch is
replayed. The unique run key, source timestamp guard, and fill-only inventory
updates make that replay safe. This is an at-least-once local delivery design;
SQLite and MySQL do not share an atomic transaction.

A received update becomes durable only after its SQLite transaction commits.
The upstream WebSocket protocol does not provide a per-message acknowledgement
or replay contract here. A connection failure, process crash, or disk failure
before that local commit can still lose an update. This logger cannot promise
end-to-end exactly-once delivery or recover every update missed while offline.

Use a persistent local disk with sufficient space for the longest expected
MySQL outage. Preserve the SQLite database and any associated WAL files during
an outage or restart. Do not delete the spool to clear a backlog. Use SQLite's
backup facilities or stop the process before copying a live spool; copying
only the main database file while WAL is active can omit committed work.
Monitor disk usage and queue growth. A full or unwritable spool must be treated
as an ingestion failure, not as an instruction to discard updates.

Run one logger instance with a stable spool path. The spool's exclusive
ownership prevents two processes from consuming the same outbox concurrently.
Different spool paths are different queues, so deployment configuration must
also prevent unintended duplicate service instances.

On SIGTERM or a normal interrupt, network producers stop and shutdown is
bounded by the current socket operation and cleanup waits. The MySQL worker
checks a stop flag between jobs and before commit, then rolls back an
unfinished batch rather than processing the rest of a large batch during
shutdown. Jobs still in the durable outbox remain available on the next start.
Twitch enrichment is best effort: metadata work may be skipped when its queue
is full or shutdown begins. Core run persistence does not depend on that
queue.

## Data semantics

- The run key is `(worldId, uuid)` throughout persistence and ARS tracking.
- Split IGT, split RTA, and context-event values are milliseconds. `vodOffset`
  is seconds. Inventory values are counts, including legitimate zero values.
- Incoming `lastUpdated` is stored as `sourceLastUpdatedMs`. Older source
  timestamps cannot roll the run back. Equal timestamps may update split and
  context values as well as fill missing fields: context changes can arrive
  while the latest main split's timestamp stays the same. The upstream field
  cannot establish ordering between updates within that same split; equal
  timestamps follow durable arrival order. Inventory still uses the first
  non-`NULL` value.
- Missing optional event values do not erase known split or context values.
  This means an absent field is not a request to delete existing data.
- All supported context events can be filled on later updates, including
  `obtainIron`, `obtainPick`, and `obtainLava`.
- Inventory is captured only when the corresponding split is the last event
  in that payload. Each stored inventory field is filled only while it is
  `NULL`; later inventory snapshots do not rewrite that recorded split. When
  `estimatedCounts` is present, an absent individual item key represents zero.
  An absent estimates map remains unknown (`NULL`). This follows the tracker's
  [positive-only estimate serialization](https://github.com/PaceMan-MCSR/PaceMan-Tracker/blob/main/src/main/java/gg/paceman/tracker/ItemTracker.java#L98-L113).
- The finish event from the original logger is `rsg.credits`. Version filtering
  retains the existing `1.16.1` behavior; a missing version is not enough to
  reject an otherwise valid update.
- `realUpdated` remains a local processing/terminal-update timestamp.
  Database `lastUpdated` retains its automatic update behavior because cache
  producers use it to find changed rows. Neither is the upstream timestamp.
- `lastPace` remains the default heartbeat concept. A successful pace commit
  updates the configured heartbeat file. A quiet feed or a database outage
  can leave it old, so its age alone does not distinguish those conditions.

ARS polling detects runs that disappear or become hidden/cheated and enqueues
terminal timestamp updates. It does not delete historical pace records or
turn hidden/cheated status into a retrospective database purge. The tracked
snapshot is persisted locally so a process restart does not forget every
previously observed live run. A failed HTTP request is retried and does not
become an empty authoritative snapshot. If a terminal touch precedes a pace
insert, a durable marker stays pending; a later run insert carries that marker
and repeats the terminal touch. Marker acknowledgement matches a transition
token so an older acknowledgement cannot remove a newer transition.
Polling only observes snapshots; a run
that appears and disappears entirely between polls cannot be detected this
way.

Twitch metadata is optional and cached by stream ID, with a fresh live-stream
check per newly enriched run so a broadcast restart cannot reuse an earlier
archive. Successfully queued enrichment is deduplicated in bounded memory.
It must not hold a database cursor or
transaction open while waiting for HTTP requests. VOD matching checks the
active stream and archive and bounds the source update's age to five seconds.
Offsets use total elapsed seconds, without modulo-day wrapping, and uncertain
or invalid offsets are skipped. Missing VOD metadata does not invalidate the
stored run. The offset anchors source `lastUpdated` to the final main event's
RTA, rather than always subtracting nether RTA. This interpretation follows
PaceMan's [latest-event conversion](https://github.com/Specnr/PaceMan.gg/blob/main/public/functions/converters.ts#L44-L78)
and [elapsed-time display](https://github.com/Specnr/PaceMan.gg/blob/main/public/functions/frontendConverters.ts#L119-L125).
It is an inference from the upstream implementation, not an independent
precision guarantee for tracker upload latency or video alignment. Stream/VOD
matching uses Twitch's [stream](https://dev.twitch.tv/docs/api/reference/#get-streams)
and [video](https://dev.twitch.tv/docs/api/reference/#get-videos) identifiers.

## Audit of the supplied script

References below are one-based lines in the user's original `Pasted text.txt`
attachment, not this replacement. Schema references use the checked-in
`13_11_2026_pace.sql` dump.

| Priority | Original lines | Finding and change |
| --- | --- | --- |
| Critical | 81–83, 207, 211–218, 262 | A single global MySQL connection is used by the WebSocket loop and ARS thread. Queries, reconnections, result buffers, and commits can interfere. The replacement gives one writer exclusive ownership. |
| Critical | 85–86, 154–205 | `SELECT COUNT` followed by `INSERT` is not atomic. The schema dump at line 615 declares `KEY uniquerun`, not `UNIQUE KEY`. Replay-safe upserts require a reviewed unique-key migration; the replacement refuses to assume that the existing index is unique. |
| High | 89–92 | An older or partial message overwrites stored splits/context with stale values or `NULL`. The replacement uses the source timestamp and preserves known values when fields are absent. |
| High | 159, 184–186 compared with 89–104 | Iron, pickaxe, and lava context values are insert-only. Events arriving after the first insert never reach those columns. They now participate in updates. |
| High | 148–149, 238–241 | Twitch exceptions prevent the entire run insertion; database failures are printed and the message is discarded. Core writes now enter a durable queue and optional metadata is separate. |
| High | 27–28, 82, 212 | Nearly ten million reconnect attempts with a three-second delay can block for roughly 347 days. Individual connection/operation waits are bounded; service retries use capped backoff. |
| High | 251–255 | ARS requests have no timeout, and any non-200 response permanently exits the polling thread. Requests now have timeouts and retry without abandoning the poller. |
| High | 257–270 | ARS identifies runs only by `worldId`, although the database lookup also uses `uuid`. Shared-world runners can overwrite each other's tracked state. Tracking now uses both values. |
| High | 215, 262–266 | A terminal touch can affect zero rows before the corresponding pace insert arrives, yet the original deletes its tracking entry. The replacement retains a durable transition marker and reapplies the touch when a later run insert arrives. |
| High | 63–64 | `timedelta.seconds` wraps negative offsets and discards complete days. A missing nether RTA also raises. Use validated values and total seconds; enrichment failure must not lose the run. |
| High | 61–64 | `lastUpdated - netherRta` is valid only if the timestamp describes nether entry. A first-seen later-split update can produce an incorrect VOD start. The replacement subtracts the latest main event's RTA, following the upstream timestamp interpretation described above. |
| Medium | 83–209, 213–218 | Error paths lack reliable cursor cleanup and rollback. Commit outcomes can be uncertain after a disconnect. Transactions now have explicit cleanup and replay-safe recovery. |
| Medium | 230, 244 | Synchronous WebSocket receive and sleep block the asyncio loop, including Twitch background work. The replacement uses asynchronous networking and cancellable waits. |
| Medium | 36–43, 66–79 | Empty event lists and missing optional fields raise exceptions; field types and MySQL integer bounds are unchecked. Validate the payload before enqueueing it and isolate malformed messages. |
| Medium | 49–55, 145–152 | Every new live run makes several uncached Twitch calls; an unavailable archive is never revisited. Optional cached enrichment removes that work from core database ingestion. |
| Medium | 224, 293–295 | Twitch startup failure can leave a non-daemon ARS thread running without the main logger. Startup and shutdown now coordinate the service tasks and resources. |
| Medium | 257–258 | Matching every old ARS run with a fresh linear scan is quadratic. Dictionary lookup makes snapshot comparison linear in run count. |
| Low | 36–43, 106–138 | Repeated event-list scans and duplicated SQL mappings increase work and maintenance risk. Normalize each payload once and generate parameterized statements from shared mappings. |
| Low | 85 | `LIMIT 1` does not make `COUNT(*)` stop after the first match. An atomic keyed write removes the existence round trip and its race. |
| Low | 237 | Full payloads are printed unconditionally although a debug flag exists. Structured, level-controlled logs reduce noise and avoid routine raw-payload output. |
| Low | 207–209 | A heartbeat filesystem error after a successful commit is reported as a database logging error. Heartbeat failures are handled separately from persisted run data. |

The original already parameterized SQL values; SQL injection through run
values is not the reason for replacing its queries. The main database risks
are concurrency, source ordering, duplicate identity, transaction cleanup,
and dropped writes.

The schema uses signed `INT` for split/context values and signed `SMALLINT` for
inventory (`13_11_2026_pace.sql`, lines 573–613). The replacement validates those
bounds rather than relying on MySQL coercion. The existing `lastUpdated`
column is `ON UPDATE CURRENT_TIMESTAMP` at schema line 600. Cache and history
jobs in this repository use that column as a change signal; the new upstream
timestamp is deliberately separate.

## Verification and deployment limits

Verified on 15 November 2026: all **131 logger, installer, configuration, local
transport, and mocked Twitch tests** passed on exact **Python 3.10.12** in an
isolated Linux container. A fresh copy of `new.py` also created its private venv,
installed dependencies, and re-executed successfully.
The missing-pip failure was also reproduced on stock Ubuntu 22.04 with Python
3.10.12, without venv bootstrap wheels: the standalone file installed the missing
support, repaired pip, preserved an existing environment marker, and passed the
then-current full suite. The latest release's generated override was accepted
by the actual **systemd 249** parser on Ubuntu 22.04; the test also reproduced
the original quoted-WorkingDirectory warning as a control. Real filesystem and
abstract Unix-domain sockets received the release's `READY=1` notification.
Tests cover notification ordering, failed startup, early exit, crash loops,
stale readiness files, and skipping already-applied DDL on setup retry.
Installer orchestration and backup failures are tested with mocks; a live
systemd service was not changed.
The earlier logger suite also passed on Python 3.11 on Windows. All **7 MySQL
8.0.46 temporary-table checks** passed. `pip check` reported no broken
requirements on Python 3.10.12. Production data and schema were
not changed; production credentials and external endpoints were not exercised.

Run the replacement's unit tests without server credentials:

```sh
python -m unittest discover -s tests -p "test_pace_logger*.py" -v
```

An optional integration check exercises the generated upsert SQL on the local
`pacestats-dev` MySQL server:

```sh
python tests/pace_logger_mysql.py
```

It requires Docker and the container's local passwordless MySQL CLI. It clones
the `pace.pace` schema into connection-local temporary tables, tests stale and
equal timestamps, missing-field preservation, late context updates, inventory
zero/first-value behavior, legacy `NULL` source timestamps, and duplicate
replay. It explicitly drops its temporary table, which would also disappear
when its connection closes. It does not modify persistent rows or schema.

The suite includes validation, SQL mappings, inventory semantics, durable queue
recovery, retry decisions, shutdown during a batch, malformed Unicode, real
loopback WebSocket authentication/message handling, streamed ARS HTTP responses,
and mocked Twitch failures/broadcast restarts. Direct dependency versions are
pinned in `requirements.txt` to the compatible versions used for this audit.
These checks do not prove production
credentials, endpoint availability, the deployed MySQL schema, or a live
Twitch archive's timestamp semantics. Use `--check` against the intended
database and review the first deployment's connection/replay logs.

After an outage, let the same spool drain; inspect recurring permanent errors
before restarting repeatedly. A malformed source payload can be rejected
individually, but a deterministic database/schema error requires an operator
fix. Avoid discarding durable jobs to silence a repeating error. Existing
historical duplicates and already-corrupted values are not repaired
automatically by installing this logger.
